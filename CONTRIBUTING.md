# Contributing to LEAPWare BuildCraft

## Runtime dependency policy — read this first

`core/` and `adapters/` are **Python 3.10+ standard library only**. A pull
request that adds a third-party runtime import to either directory, or to
any plugin's `bin/` script, will be closed without review. `pytest` is the
one dev-only exception, used solely under `tests/`.

## Adding a rule

1. Write it under `core/lwb_core/rules/<rule_id>.py`. It must expose
   `rule_id: str` and `evaluate(event, config) -> Optional[Finding]`, and it
   must be pure — no file I/O, no network, no clock.
2. Register it in `core/lwb_core/rules/__init__.py`'s `RULES` list.
3. Add unit tests under `tests/core/`, including a case for each of `off`,
   `warn`, and `deny` mode, and a case proving the rule returns `None` (not
   a false positive) for events it has no opinion on.
4. Document it under `docs/rules/<rule_id>.md`, describing what it checks,
   its `options`, and its default mode.
5. Run `python scripts/lwb_build.py` so both plugins' `vendor/` trees pick up
   the new rule, then `python scripts/lwb_build.py --check` to confirm.

## Workflow

```
python -m pytest -q
python scripts/lwb_build.py --check
python scripts/lwb_validate_claude_plugin.py
python scripts/lwb_validate_codex_plugin.py
```

All four must pass before opening a pull request. CI (`.github/workflows/ci.yml`)
runs the same four checks on a Windows/macOS/Ubuntu x Python 3.10/3.12
matrix.

## Commit and PR conventions

- One logical change per commit; write the "why", not just the "what".
- Reference the issue a PR closes, if one exists.
- Do not hand-edit a `vendor/` directory — it is generated by
  `scripts/lwb_build.py` and CI will catch drift.
